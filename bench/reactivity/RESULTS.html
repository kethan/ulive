What was wrong before, and how it was proved

The old core kept an internal effect inside every computed, so a write pushed the new value down every path of the graph. A node with two dirty inputs recomputed once per path and ran its effects once per path — the first run seeing a half-updated graph. That is what the harness counts as a delivery mismatch.

ulive (eager)  diamond: b×1 c×1 d×2 recomputes per write (ideal 1/1/1) | effect saw [4,5] (ideal [5])
ulive (eager)  4x3 torus: 60 recomputes for one write (ideal 16)
ulive (pull)   diamond: b×1 c×1 d×1 recomputes per write (ideal 1/1/1) | effect saw [5]
ulive (pull)   4x3 torus: 16 recomputes for one write (ideal 16)
preact         diamond: b×1 c×1 d×1 recomputes per write (ideal 1/1/1) | effect saw [5]
preact         4x3 torus: 16 recomputes for one write (ideal 16)

The fix: a write only marks the nodes that read it dirty and queues the affected effects; a computed recomputes when it is read, at most once per cascade. A write made while a flush is running joins that flush instead of recursing into it.

Two behaviours changed on purpose: a diamond delivers [4, 7] instead of the glitchy [4, 5, 7], and a computed that throws surfaces the error when its value is read, not when the source is written — which is what Preact, Solid and alien-signals do too.

Caveats

  • quick profile, one round, ≤100 samples. Sub-millisecond rows reached 100% coefficient of variation (pure pull: 0.8 / 1.6 / 3.2 ms across three runs of the same build) — read anything under ~1.5× as a tie. Rows in the hundreds of ms are stable.
  • lifecycle/* needs a native owner scope (createScope); ulive has no graph-level disposal, so those two rows are empty for ulive, Preact and uSignal.
  • The first pass of this benchmark used withBatch: fn => fn(). That was my adapter bug — ulive does have batch — and it produced out-of-memory rows. With the real batch() those rows pass even on the old core; the three semantic failures were real.
